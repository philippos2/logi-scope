# 最終確認チェックリスト

最新mainを対象に、既存の検証結果と今回の確認を区別して記録する。このチェックリストだけでは検証済みとしない。v0.3.0の既存環境での確認結果と未実施範囲は[最終動作確認記録](history/final-runtime-verification.md)を参照する。

## 準備と再現性

- [ ] 対象コミット、ホスト・モデル、実施日を記録する。
- [ ] [セットアップガイド](getting-started.md)の環境準備・DB初期化・seed・ingest・APIとReactの起動手順が現在の設定と一致することを確認する。
- [ ] 最新コードでAgent APIを再起動する。起動済みプロセスが古い設定を保持していないことを確認する。
- [ ] 通常データの確認前に更新用荷物を除去し、荷物90件と状態別内訳を確認する。更新・調査の送信を止めてから管理操作を行う。

初期化・除去は[配送更新手順](delivery-updates.md#初期化終了と自動検証)を参照する。既存環境の確認と、別の空DB・キャッシュからの再現性確認を混同しない。空環境の再確認が未実施なら、過去の[再現性検証](history/reproducibility-verification.md)を参照したことと未実施の範囲を記録する。

## Agentの5シナリオ

API・LLM・通常seed・索引を準備し、ホストから実行する。

```bash
docker compose exec app uv run --locked python scripts/verify_demo.py --repeat 2
```

- [ ] A：配達完了、荷物の根拠、Tool履歴、空の未解決事項。
- [ ] B：顧客・荷物・イベントと対応する障害報告に基づく遅延原因。
- [ ] C：問い合わせチャンクだけでなく問い合わせ501の正本も取得・引用。
- [ ] D：不存在を捏造せず、検索履歴と未解決事項を提示。
- [ ] E：同名顧客の候補を提示し、任意選択せず追加情報を求める。
- [ ] 成功件数／実行件数と失敗理由を記録する。各2回なら計10件。回答文の完全一致やTool順序の固定は要求しない。

## 配送更新と画面

- [ ] `updates-init`と更新サービスを準備し、SHP-UPDATE-001の更新前の状態を調査する。
- [ ] 画面から配達完了を報告し、明示的な再調査で配達完了・根拠・履歴を確認する。以前の回答は自動更新されない。
- [ ] [更新検証スクリプト](delivery-updates.md#初期化終了と自動検証)を実行する場合、画面操作後に再初期化し、他の更新操作と同時に実行しない。更新前・更新と再送・更新後の計3件を確認する。
- [ ] PCとスマホ幅で、質問・結果・報告欄の表示を確認する。実機スマホの確認と区別する。
- [ ] 確認後のデータ状態を記録する。通常の集計を行う場合は更新用荷物を除去する。

同時更新・ロール権限・単一Toolのスナップショット・再送・タイムアウトの異常系は自動テストの検証範囲として確認する。全異常系をブラウザで再現したとは扱わない。

## 結果の残し方

公開応答はGit対象外の`artifacts/`、日時・対象コミット・成功件数・未実施範囲は`docs/history/`へ記録する。資格情報、モデル内部推論、生LLM応答は保存しない。最新mainのCI成功も確認する。
