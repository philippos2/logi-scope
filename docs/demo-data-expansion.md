# デモデータの構成と検証

## 目的

データはseedと文書正本に収録している。現在の収録内容は[架空デモデータ](demo-data.md)を参照する。単に件数を増やすのではなく、対象の特定、複合条件、業務データと文書の横断、情報不足を示すケースを増やす。

## 規模と配分

通常のseedは顧客30件・荷物90件・問い合わせ20件・文書13本で構成する。荷物の状態別件数は配送中49件、配達完了27件、遅延10件、所在不明4件。拡充前後の配分と作業経緯は[検証履歴](history/demo-data-expansion.md)に記録している。

荷物には配送イベントを用意し、配達完了・遅延・所在不明には状態を裏付けるイベントを設ける。配送イベントの総数は177件。事故は配送状態の新しい値にせず、配送イベントと事故報告書に記録する。

## 検証ケース

| ケース | データの構成 | 検証する振る舞い |
|---|---|---|
| 同名顧客 | 顧客401〜416のうち4件は、名前が同じで営業所が異なる2組 | 名前だけなら追加情報を求め、営業所指定後は対応する顧客を特定する |
| 複数荷物 | 顧客401〜416に配達完了と配送中の荷物を関連付け、一部には遅延・所在不明も含める | 顧客と状態を組み合わせ、対象外の荷物を混ぜない |
| 問い合わせ有無 | 8荷物に各1件の問い合わせを作り、残りのSHP-EXPAND荷物には問い合わせを作らない | 問い合わせなしでも業務データから回答し、存在しない問い合わせを生成しない |
| 遅延・事故 | SHP-EXPANDの遅延6荷物を3件ずつ2原因に分け、対応する報告書2本に対象荷物・障害IDを明記する | 別原因の報告書を取り違えず、配送イベントから対応する文書を調べる |
| 遅延FAQ | 遅延案内FAQに、原因が判明していても到着予定が未確定な場合の案内を用意する | 一般的な案内と個別荷物の事実を区別し、FAQから到着時刻を作らない |
| 所在不明 | SHP-EXPANDの所在不明2荷物は現物確認できず調査中とし、原因・発見予定は未確定にする | 紛失・盗難を断定せず、根拠に応じて情報不足を示す |
| 該当なし | 顧客内に存在しない配送状態、seedに含まれない荷物IDを質問する | 検索して0件を確認する。一覧の0件と個別IDの不在を区別する |

顧客401〜416の同名組は既存顧客と名前を重複させない。既存A〜Eの顧客・荷物・問い合わせ・文書のIDと本文、既存顧客に属する荷物数は維持する。文書と業務データの意図的な矛盾は、対処方針の設計が必要なためデータに含めない。

## 命名と参照

- 顧客名は既存と同じく架空の法人名に`デモ`を付け、営業所・拠点・配送先に`架空`を付ける。個人名・実在企業名を使わない。
- 対象の顧客IDは401〜416、荷物IDは`SHP-EXPAND-001`〜`SHP-EXPAND-056`、イベントIDは3001以降、問い合わせIDは701〜708を使用する。
- 報告書の障害IDは`INC-EXPAND-001`・`INC-EXPAND-002`とし、対応する配送イベント・問い合わせ・文書で同じIDを使う。
- 時刻は架空の2026年10月の記録とし、タイムゾーンを既存形式と揃える。件数・状態そのものにタイムゾーンは付けない。
- 同名組はデモ銀河資材（401・402）とデモ霞色商会（403・404）。接触事故と橋梁点検による遅延を用意し、質問例は[架空デモデータ](demo-data.md)に記載する。

## データ準備

管理用seedと手動ingestで業務データ・派生インデックスを準備する。[実行ガイド](getting-started.md)の手順を参照する。データ変更後は既存A〜Eと質問例の期待事実を確認し、結果の取得上限と総件数を区別する。

## 検証状態

データは管理用seedで投入し、手動ingestで39チャンク・33正本から派生インデックスを再生成した。自動テストと実モデルの結果・条件は[拡充の検証履歴](history/demo-data-expansion.md)に記録する。
