# LogiScope — AI Agent PoC 要件・制約・受入条件

本書はLogiScopeの要件・制約・受入条件を記載する。具体的な実現方法・検証範囲は[design.md](design.md)に分ける。構成の具体化は可能だが、以下の目的・アーキテクチャ制約・受入条件の変更は理由を説明して提案する。

## 1. 目的

物流会社の業務を題材とするAIエージェントの公開デモを作る。実運用サービスではなく、自然言語の問い合わせに対し、LLMが情報源・Toolを選択し、その結果を観測して次の操作または最終回答を判断する **Tool-calling Agent Loop** を実証する。

示す内容は、構造化業務データと非構造化文書の横断、複数段階の調査、AIによるTool選択、根拠付き回答、情報不足・曖昧性、Loop制御、ローカル再現性である。問い合わせ種類ごとの固定フローをハードコードしない。

## 2. アーキテクチャ制約

### データベース

業務データとベクトル検索を同じPostgreSQLに置き、pgvectorを使う。専用Vector DBは追加しない。

### LLM

ホストPC上でローカル実行し、OpenAI互換APIで接続する。有料クラウドLLM APIを必須としない。接続先と使用モデルは設定で変更できる。低遅延は前提とせず、問い合わせに相応の時間がかかることを許容する。実装初期に採用モデル・実行環境でTool Callingが実用上成立するか検証する。

### エージェント

LLMに利用可能なToolを提示し、Tool結果をLLMへ戻す。次のToolまたは最終回答をLLMが判断する。Loopは以下を備える。

- 最大実行ステップ数。
- 同一操作の重複検出。
- Tool引数検証と、不正な引数に対する限定的な修正再試行。
- Tool実行失敗時の制御されたエラー処理。
- 最大ステップ到達時の打ち切り処理。

Chain-of-Thoughtなど内部推論は記録・公開しない。外部の実行履歴は、実際に実行されたTool・引数・成功/失敗という操作履歴に限定する。

### Tools

Agentが利用するToolは読み取り専用。少なくとも以下の能力を持つ。具体的な名前は設計で定める。

- 顧客検索。
- 荷物検索と、配送状況・配送イベントの確認。
- IDによる問い合わせ正本の取得。
- 文書と過去問い合わせの派生チャンクに対する非構造化検索。

業務データへの読み取り専用アクセスは、アプリの約束に加えてDB権限で担保する。

## 3. データ要件

すべて架空データとし、実在する顧客・企業・荷物・事故などの情報を使わない。業務情報は顧客、荷物、配送状況・イベント、顧客問い合わせを含む。文書はFAQ、マニュアル、遅延報告、事故・障害報告を含む。

業務データ、問い合わせ、文書、利用者の質問、回答は日本語を主要言語とする。日本語での検索・回答がデモで実用上成立すること。

## 4. 正本と派生データ

- 顧客・荷物・配送イベント・問い合わせ: PostgreSQLの業務テーブルが正本。
- FAQ・マニュアル・遅延/事故報告: リポジトリ内の文書ファイルが正本。
- chunks・embedding: 検索用の派生データ。正本として扱わず、正本から再生成できること。

過去問い合わせをベクトル検索した結果には、対応する問い合わせの正本を取得するための識別情報があること。文書由来と問い合わせ由来の両方をingest対象とする。

## 5. API

HTTP APIの`POST /agent`で質問を受け取り、同期的に最終JSONを返す。利用者がToolや検索手順を指定する必要はない。

```json
{"question": "顧客Aの荷物が遅延している原因を調べてください"}
```

## 6. 応答形式

最終応答は少なくとも以下の4項目を含む。

```json
{"answer": "...", "sources": [], "steps": [], "unresolved": []}
```

- `answer`: 利用者への最終回答。
- `sources`: 回答の根拠となる業務データ・文書の追跡可能な識別情報。
- `steps`: 実際に実行されたTool、渡した引数、成功/失敗。内部推論は含めない。
- `unresolved`: 回答不能、情報不足、対象を一意に特定できないことなどを機械的に識別する情報。

具体的な配列要素の契約は設計書で定める。

## 7. 基本動作

質問だけを受け取り、必要に応じて顧客特定、荷物検索、配送状況確認、関連報告検索、情報統合を行う。これは実行例であり、固定の処理順序ではない。Toolの選択・回数・順序はLLMが判断する。

## 8. 不明・曖昧な情報

存在しない事実を作らない。取得した事実の照合・統合は行うが、関連を裏付ける情報のない事故報告から対象荷物の原因を断定しない。

情報不足では`answer`で確認できない範囲を説明し、`unresolved`へ未解決事項を入れる。複数候補が存在するときは任意の候補を選ばず、複数候補と特定に必要な追加情報を示す。確認できる部分の回答と未解決事項は併存できる。

## 9. デモシナリオと受入条件

次の5シナリオを再現可能な架空データで用意する。回答の完全一致や不要な固定Tool順序ではなく、以下の振る舞いで合否を判定する。

### A. 単純検索

一つの業務検索で回答可能な質問を用意する。正しい業務データに基づく回答、追跡可能な`sources`、実行Toolを含む`steps`、空の`unresolved`が必要。

### B. 複数段階の調査

顧客・荷物・配送状況・関連報告などを段階的に調べるデータを用意する。複数Toolを実行し、前段の結果を後段の検索に利用すること。業務データと文書を統合し、双方の根拠と複数段階の履歴を追跡できること。遅延原因を確定するデータには、対象荷物と事故の関連を裏付ける情報を持たせる。

### C. 非構造化検索 → 正本取得

類似問い合わせを非構造化検索で発見し、その識別情報から正本を取得するデータを用意する。派生検索結果だけで終了せず、取得した正本を最終回答へ反映すること。`sources`から検索対象と正本の両方を追跡できること。

### D. 回答不能

存在しない荷物等を質問する。存在しない情報を作らず、確認できないことを回答する。`unresolved`は空でなく、`steps`で実際の検索を確認できること。

### E. 曖昧性

同名顧客などを用意する。任意の候補を選ばず、複数候補を回答し、`unresolved`で特定に必要な情報を識別できること。

## 10. 自動テスト

個々のTool正常系、入力異常系、多段Loop、重複反復防止、Tool例外、最大ステップ、情報なし、曖昧な対象を検証する。

ローカルLLMを毎回起動せず主要な制御を検証できる設計とする。決定論的な自動テストと実LLMの接続・デモ検証を分離する。実DBの型・検索・権限を確認する統合テストも用意する。

## 11. 再現性

第三者がREADMEに従って環境準備、架空業務データ投入、文書・過去問い合わせの派生データ生成、ローカルLLM接続、アプリ・React画面の起動、ブラウザまたはcurlでのデモ、自動テストを実行できることを目標とする。

LLM・埋め込みモデル本体をGitへ格納しない。検証したモデルと実行条件、依存関係の版を記録する。

## 12. README

目的、概要、正本/派生、Loop、セットアップ、データ準備、起動、画面操作とcurl例、テスト、5シナリオ、Known Limitations、本番化時の追加事項を記載する。設計段階と実装済みを区別する。

基本表現はTool-calling Agent Loopとする。「ReActを完全実装した」など、実装以上の主張をしない。

## 12.1. デモ用フロントエンド

Reactの最小Web画面を同じリポジトリに追加する。自然言語の質問を既存の`POST /agent`へ送り、実行中の状態、回答、根拠、実行済みTool履歴、未解決事項とAPIエラーを表示する。5シナリオの質問例を選べるようにする。画面側でToolの順序・検索フローを指定しない。ストリーミングや会話セッションは追加しない。

受入条件は、画面から質問してAPIの4項目を確認でき、実行中の重複送信を防ぎ、失敗時に成功を装わず再操作できること。API版のA〜Eの受入条件も維持する。配置・表示・操作の具体化は[フロントエンドUI設計](frontend-design.md)に記載する。

## 13. 対象外

モバイル専用アプリ、ユーザー認証、マルチテナント、本番デプロイ、大規模分散システム、大規模負荷試験、実データ・個人情報、本格的な個人情報保護機構、Agentによる業務データ更新/削除、外部業務システムへの破壊的操作、ストリーミング、バックグラウンドジョブ基盤、本格的な監視・可観測性・AI評価基盤、高度な検索精度改善、モデル学習/ファインチューニング、モデル本体の格納、有料クラウドLLMへの必須依存、専用Vector DB、Graph DB、PoCに直接必要のない追加機能。

不可能だからではなく、デモの目的に不要なため除外する。

## 14. 採用技術と設計方針

FastAPI、SQLAlchemy、Alembic、pytestを採用する。目的、アーキテクチャ制約、正本/派生の関係、Loop方針、読み取り権限、API仕様、受入条件は変更しない。

データ検証、接続クライアント、埋め込み、ディレクトリ、設定管理、補助ライブラリの詳細は、要件に合う標準的で過剰でない構成を選び、理由を記録する。

## 16. ローカル配送更新デモの追加範囲

AgentのToolと接続は読み取り専用のまま維持し、専用ロール・専用APIから更新用荷物の配送イベントと状態だけを変更する。既存React画面の報告欄またはcurlから専用APIを呼ぶ。固定シナリオと更新データを分離する。重複送信・時刻逆転・同時更新・状態遷移・トランザクションの整合を検証する。画面では報告と調査の同時送信を防ぎ、受付結果が不明な場合は同じイベントキー・内容で再送できること。報告後の状態は明示的な再調査で確認する。問い合わせ・文書・埋め込みは更新しない。配送員専用アプリ、外部連続受信、キュー、本番認証・デプロイは追加しない。詳細は[配送更新デモ設計](delivery-updates.md)を参照する。
