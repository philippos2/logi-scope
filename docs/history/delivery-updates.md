AgentのToolや読み取り専用接続は変更せず、専用FastAPIサービスと`logi_scope_updater`で配送状態・イベントを更新する。ホストの`.env`はマウントせず、更新用資格情報はupdatesと管理サービスだけへ渡す。固定の90件とは別に更新用荷物を1件作成・除去できる。問い合わせ・文書・派生索引は更新しない。

## 検証結果

- DB統合を含む自動テストは240件中240件成功。新規登録・同一再送・内容の衝突・時刻逆転・状態遷移・同時送信・異なる同時更新・書き込み後の失敗によるロールバック・DB権限・入力検証・公開エラーを確認した。
- 実コンテナの資格情報分離はapp・ingest・manage・updatesの4件中4件成功。値は出力しない。
- Ruff・Compose設定確認・`alembic check`成功。
- 実API・実LLMの確認は3件中3件成功。更新前の配送中回答、配達完了への更新と同一キー再送、更新後の配達完了回答を確認した。LLM呼び出しは更新前後の2件であり、更新APIの処理自体はLLMを使わない。

公開応答はGit対象外の`artifacts/delivery-update-verification.json`へ記録した。モデルは既存のOllama `logiscope-qwen30-probe`（Qwen3 30B-A3B Instruct、8192コンテキスト）、WSL・RTX 3060 12GB。内部推論や生LLM応答全体は保存していない。確認後に更新サービスを停止し、更新用データを除去して通常の90件へ戻した。

UI、認証、外部受信、順不同の自動補正、更新による自動再質問は追加していない。既存React画面は調査専用である。ローカルの架空データ実演であり、本番の配送イベント基盤を実装したという主張ではない。
