# 対象未指定の荷物調査の修正

検証日: 2026-10-06。作業ブランチ: `feature/agent-target-grounding`。

## 問題と修正

利用者の「荷物の配送状態を教えて」に、指定されていない`SHI123456789`の不存在を回答する事象が再現した。元の実行履歴は提供されていないため、元のTool呼び出し列までは確定していない。実装を調べると引数の型は検証していたが、検索する荷物IDの出所は検証していなかった。

質問または成功した取得結果で確認できない荷物IDは、業務Toolの実行前に拒否する。対象を捏造して検索せず、`ambiguous_target`と荷物ID・顧客情報の追加指定案内を返す。未実行の拒否は`steps`に含めない。対象情報が不足すると判断したLLMはToolを呼ばずに追加指定を求めることもできる。

質問中のID、顧客検索から取得した荷物参照、問い合わせの荷物ID、取得した文書本文のIDは後続調査に使用できる。IDの一部だけの一致や、前のリクエストで取得したIDは許可しない。Toolの選択順序は固定していない。

## 検証

- 実DB統合を含む自動テスト: 165件中165件成功、スキップなし。
- 出所のないIDの拒否、IDの部分一致、同一バッチ内の未実行IDの再利用、問い合わせ・文書からのID引き継ぎ、リクエスト間の分離を検証した。
- 既存テストで暗黙に与えていた荷物IDは質問に明記し、元の制御・例外処理の期待値は維持した。
- 最終実装で、実Ollama・Qwen3 30B-A3B Instruct-2507 Q4_K_Mに問題の質問を3回送信し、3件中3件成功。全件で追加指定を求め、`sources`・`steps`は空、`unresolved`は`ambiguous_target`。所要時間は6.08秒、2.67秒、2.38秒。

初回の既存A〜E検証は自動判定3件/5件成功。Aは正しい「配達済み」を判定器が見落としており、同義表現の受入と誤った「配送中」の拒否を検証するテストを追加した。この修正で同じ応答の判定は4件/5件となった。Dは指定済みのIDにも追加指定を求めていたため、指定されたIDは実際に検索してから不存在を判断するようプロンプトを明確にした。この時点の再実行は4件/5件成功し、Dは検索せずに回答を終了していた。未検索で受け入れられない回答については、Toolを利用できる再試行を1回だけ通常の呼び出し予算内で認めるようLoopを補正した。その後のA〜Eは4件/5件成功で、Dは依然として検索を省略した。対象IDの出所・指定済みIDの検索・対象未指定時の確認を簡潔な3行へ整理すると、D単独の追加確認は2件/2件成功した。途中の結果は破棄せず保持している。

最終実装でA〜Eを改めて実行し、5件中5件成功、失敗・スキップなし。業務データと文書の根拠、IDの引き継ぎ、問い合わせ正本の取得、Dの不存在ID検索、Eの候補非選択を既存の受入条件で確認した。
