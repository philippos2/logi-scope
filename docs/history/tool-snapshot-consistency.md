# 単一Tool内の配送詳細の整合性

2026年10月6日、静的レビューで、荷物と配送イベントを別々のSELECTで取得する間に更新がコミットされると、状態とイベントの観測時点がずれる問題が指摘された。

読み取りエンジンの分離レベルをREPEATABLE READへ変更し、同じToolのトランザクション内では同一スナップショットを使う。Tool終了時にセッションを閉じるため、次のToolでは新しい状態を参照できる。LLM待ちの間にトランザクションを保持せず、複数Tool間の観測時点の一致は保証しない。

回帰テストでは、荷物のSELECT直後に実更新APIの処理を別接続でコミットし、現在のToolが更新前の状態・イベントを揃えて返すことと、次のToolが更新後の状態・イベントを返すことを確認した。

- 配送更新関連の実DBテスト：9件中9件成功。
- 専用の空PostgreSQLにマイグレーション・通常seed・決定論的検索チャンクを投入した全自動テスト：241件中241件成功。
- RuffとAlembicの差分確認：成功。
- 実LLMとブラウザ操作は今回再実行していない。

初回の全テストはデモDB上で237件成功・4件失敗した。手動確認済みの更新用荷物が残り、固定90件の集計とダウングレード検証の前提に一致しなかったためである。デモデータを残したまま、別Composeプロジェクトの空DBで全件を再確認した。検証用コンテナとボリュームは終了後に除去した。
