# 要件・設計文書の整理

2026年10月7日、通常の文書を現在の仕様・設計の説明へ整理した。要件・受入条件・実行設定は変更していない。デモ動画の台本は制作資料として保持し、READMEの文書一覧からリンクを外した。

## 初期の要件レビューと作業方針

以下は実装開始前の方針・決定経緯であり、現在の機能説明とは区別する。


[要件](../requirements.md)は公開デモのPoCとして実現可能。FastAPI・SQLAlchemy・Alembic・pytestを既存合意として固定した。配送イベント確認、過去問い合わせのingest、IDによる正本取得を能力要件へ明記した。

検索結果の統合と、存在しない事実の生成を区別する。類似事故報告だけで遅延原因を断定しない。5シナリオは必要な振る舞いを検証し、固定Tool順序を実装しない。


### 実装開始前の方針


要件の矛盾、未確定事項、技術選定、全体構成、ローカルLLMのTool Calling検証方法、実装順序を整理してから実装する。レビュー結果と明確化を[設計書](../design.md)に記録する。


### データ拡充の作業手順


1. `seed/business.json`へ新規レコードを追加し、3文書を追加する。ID重複、FK、状態別件数、イベントと報告書の対応を確認する。
2. 実DB統合テストの固定集計値を新しい配分へ更新する。既存のmissing・delayedの全体一覧テストは取得上限と追加結果を考慮し、既存の個別・顧客指定条件を維持する。新規同名組、問い合わせ有無、複合条件、取得上限を超える件数を検証する。
3. 自動テスト・Ruffを実行する。必要な検証は実PostgreSQLで行い、単なるseedの値の再記述だけのテストにしない。
4. 管理用seedを適用し、手動ingestで文書・問い合わせの派生データを全件再生成する。Agentの読み取り専用権限を維持する。実行手順は[実行ガイド](../getting-started.md)を使う。
5. `verify-demo-scenarios`の手順で既存A〜Eを再検証する。文書追加による検索順位の変化も確認し、成功数・失敗を記録する。
6. 全体集計90件と状態別内訳、同名顧客の営業所指定、問い合わせのない荷物、新規の2種類の遅延原因、所在不明の情報不足を実LLMで確認する。検索結果の`limit`・`truncated`と集計値を区別できることを確認する。
7. 実LLMの経過時間、コンテキスト上限8192での失敗有無を記録する。結果の上限を増やして解決せず、必要な対象・文書に絞るTool選択を確認する。観測していない性能は主張しない。
8. `demo-data.md`・必要なREADME案内を実装済みの内容に更新し、実測と修正経緯を`docs/history/`へ残す。


拡充前後の件数・実測結果は[データ拡充の検証履歴](demo-data-expansion.md)を参照する。
