# LogiScope — フロントエンドUI設計

状態: UI設計。Reactの質問入力・調査結果の画面は実装済み。利用者提供のClaudeによるUI案を、既存APIの契約と制約に照合して補正した。

## 1. 前提と範囲

確定方針はReactを使い、同じリポジトリの`frontend/`に置くこと。運送会社の社内担当者によるPC利用を中心に設計し、スマホはレスポンシブ対応とする。実際の利用比率を測定したものではない。

自然言語の質問を既存の`POST /agent`へ送り、`answer`、`sources`、`steps`、`unresolved`を表示する。画面側にTool選択・検索フローを実装せず、LLMやDBへ直接接続しない。認証、会話履歴、複数セッション、ストリーミング、スマホ専用アプリ、エンドユーザー向け画面は対象外。Tool結果の本文はAPIが返さないため表示しない。

要件は[requirements.md](requirements.md#121-デモ用フロントエンド)、サーバ側の契約は[design.md](design.md#4-api契約)を参照する。以下の配置・配色は初期実装の設計案であり、受入条件を維持する範囲で調整できる。

## 2. レイアウト

### PC

ヘッダーにLogiScopeと「物流業務の調査エージェント（デモ）」を表示する。本文は左約60%・右約40%の2列とする。

- 左: 質問入力、送信操作、5つのサンプル質問、回答、未解決事項、根拠。
- 右: 実行履歴と、折りたたんだAPIレスポンスJSON。

右ペインは十分な画面幅・高さがある場合に`position: sticky`で追従させる。小さい画面や拡大表示では通常配置に戻す。長い内容を隠したり、回答を覆ったりしない。

### スマホ

質問、サンプル質問、回答、未解決事項、根拠、実行履歴、JSONの順に1列で配置する。根拠・実行履歴・JSONは初期状態で閉じる。サンプル質問は横スクロール可能とし、各ボタンへキーボードでも到達できるようにする。

PCとスマホで同じデータと部品を使う。長い識別子・日本語本文は折り返し、JSONは必要な場合に領域内で横スクロールさせる。ページ全体の横はみ出しを防ぐ。

## 3. 入力と送信

複数行の入力欄を使用する。空白除去後1〜4,000文字とし、空入力・文字数超過・送信中は送信を無効にする。入力欄にラベルと文字数を表示する。

送信ボタンとCtrl/Cmd+Enterで送信する。日本語IMEの変換確定中にはショートカットで送信しない。サンプル質問は入力欄へ設定するだけで、自動送信しない。送信中はサンプル質問も無効にする。

新規送信時に前の結果を消し、送信した質問を保持して結果に添える。以後入力を変更しても、回答がどの質問に対応するか分かるようにする。通信失敗時も入力内容は保持する。

| シナリオ | ボタン名 | 質問文 |
|---|---|---|
| A | 単純検索 | SHP-DEMO-002の配送状態は？ |
| B | 多段調査 | デモ青空商店の荷物が遅延している原因は？ |
| C | 正本取得 | 配達完了後の受領確認について、過去の問い合わせでの対応を調べて |
| D | 回答不能 | SHP-NOT-FOUNDの配送状態は？ |
| E | 曖昧性 | デモ双葉商会の荷物を調べて |

質問文の参照元は`scripts/verify_demo.py`のCASES。変更時にはデモデータ・受入検証との整合性を確認する。

## 4. 状態と待機

| 状態 | 表示・操作 |
|---|---|
| 初期 | 質問入力とサンプル質問。結果領域には未実行の案内 |
| 送信中 | 経過秒数と「ローカルLLMのため数分かかる場合があります」。送信無効、履歴は「完了後に表示されます」 |
| 応答受信 | 回答・根拠・履歴を表示。未解決事項があれば回答直下へ表示 |
| Tool失敗を含む応答 | 該当ステップを失敗表示。回答と未解決事項は保持し、全体を一律に失敗扱いしない |
| HTTP・通信エラー | エラー表示と再操作可能な入力欄。成功結果として表示しない |
| 待機終了 | 応答待ちを終了した旨と、サーバ側の調査が続く可能性を表示 |

応答は一括返却されるため、実行中にTool名・進捗率を推測して表示しない。経過時間はブラウザ側の待機時間であり、モデル推論時間の実測ではない。

### 待機終了とタイムアウト

ボタン名は「待機を終了」とし、ブラウザ側の通信を中断する。現APIには調査キャンセル機能がないため、サーバ側の調査やLLM推論が停止したとは表示しない。

ブラウザ側のタイムアウトは初期960秒とする。サーバの初期値はLLM要求1回300秒・調査全体900秒であり、ブラウザは調査全体の上限に余裕を加える。サーバの全体上限を変更した場合は画面側の設定も確認する。プロキシ経由でも長い要求を途中で切らないよう設定を確認する。

通信切断・待機終了・タイムアウトの後もサーバが調査を続け、再送が`agent_busy`になる場合がある。自動再送はしない。古いリクエストの応答が新しい画面状態を上書きしないよう、要求ごとに状態を管理する。

## 5. 結果の表示

| 部品 | データ | 表示 |
|---|---|---|
| 回答 | answer | 改行を保持したテキスト |
| 未解決事項 | unresolved | 日本語の説明、code、message。空でないdetailsは折りたたんで表示 |
| 根拠 | sources | 件数、種別、識別情報。追加情報は展開表示 |
| 実行履歴 | steps | 実行順の番号、tool、成功/失敗。argsとerrorは展開表示 |
| APIレスポンスJSON | 全応答 | 初期状態で閉じる。表示するのは公開API応答のみ |

APIの本文をHTMLとして実行しない。回答は通常のテキストとして表示し、Markdownレンダリングは初期範囲に含めない。

### 根拠

| kind | 表示名 | 主な識別情報 |
|---|---|---|
| customer | 顧客 | id |
| shipment | 荷物 | id |
| delivery_event | 配送イベント | id |
| inquiry | 問い合わせ | id |
| chunk（pathあり） | 文書 | pathのファイル名 |
| chunk（pathなし） | 問い合わせ本文 | origin_id |

未知のkindはその値を表示する。path、chunk_id、source_revisionなどは存在する場合に展開表示する。チャンクごとの根拠は同じ文書に由来しても黙って削除しない。

根拠は参照情報であり、現APIには文書・レコード本文を開くエンドポイントがない。未提供の詳細画面やリンクを作動するように見せない。

### 実行履歴・未解決事項

Tool名と識別子は等幅で表示する。引数は初期状態で閉じ、項目名と値を表示する。nullは「未指定」と薄い色で表示するが、読めるコントラストを確保する。失敗時は`error`の公開コードも表示する。内部推論は表示しない。

`not_found`は「対象が見つからない」、`insufficient_evidence`は「情報不足・未確定」、`ambiguous_target`は「対象の特定が必要」と表示する。その他のコードも日本語の説明と元のコードを併記する。複数の未解決事項をすべて表示する。

曖昧性のdetailsには`required_fields`、`candidates`、`truncated`が返る。候補のid・name・branchを表示し、顧客IDまたは営業所の指定を案内する。候補省略時は一覧が全件ではないと明記する。候補を画面側で自動選択しない。追加情報を含めた質問は新規リクエストとして送る。

## 6. エラーとヘルスチェック

| 状態 | 画面の案内 |
|---|---|
| 422 | 入力内容を確認。detailが入力エラー配列である形式にも対応 |
| 502 / llm_unavailable | LLMから回答を取得できない |
| 504 / llm_timeout | LLMへの要求が時間超過 |
| 503 / agent_not_ready | Agentの準備ができていない |
| 503 / agent_busy | 別の調査を実行中。しばらく待って再操作 |
| 通信失敗・その他のエラー | 接続を確認し、必要なら再操作 |

HTTP 200でもunresolvedが空とは限らない。回答不能・曖昧性・部分回答はHTTPエラーと区別する。不正な応答形式を成功として表示しない。

`GET /health`は`{"status":"ok"}`を返す生存確認であり、DB・LLM・検索索引の準備状態を保証しない。初期画面では「Agent利用可能」を示すヘッダー状態表示を設けない。

## 7. 見た目とアクセシビリティ

明るい背景と落ち着いた配色、日本語対応のシステムフォントを使う。成功・失敗・未解決は色に加えて文字でも示す。

折りたたみ、送信、待機終了、サンプル質問はキーボードで操作できる部品とする。フォーカスを見えるようにし、入力欄にはラベルを付ける。画面幅が変わっても折りたたみの操作や読んでいる位置を不必要に失わせない。

開始・完了・待機終了は通知領域、エラーは適切な通知領域で伝える。経過秒数は毎秒読み上げさせない。

## 8. 検証と実装前の決定事項

画面の決定論的テストでは、正常応答、複数の未解決事項、Tool失敗、曖昧性、HTTP・通信エラー、入力制限、重複送信防止、待機終了後の状態を確認する。実LLMを毎回テストで実行しない。

ブラウザではPC・スマホ幅、キーボード操作、日本語入力を確認する。結合確認では画面からA〜Eを実行し、サーバ側の既存テストも維持する。偽APIによる画面テストと実LLMの受入結果は分けて報告する。

実装前にReact周辺の構成・版、依存ロック、開発用APIプロキシ、Docker起動方法、CIの画面テスト・ビルド追加を決定し、[全体設計](design.md)と[セットアップガイド](getting-started.md)へ反映する。基盤としてReact＋TypeScript＋Vite、Node.js 24 LTS、npmのロックと`npm ci`、Compose開発コンテナ、APIプロキシ、CIの型チェック・ビルドを採用済み。画面テストはVitest＋React Testing Library＋Happy DOMを採用し、Vite設定との互換性とDOM操作の検証を簡潔に保つ。

## 9. UI実装の確認項目

作業ブランチは`feature/demo-frontend`。基盤はmainへ統合済み。以下の1〜6のコードとCI設定は実装済み。プロキシ経由の実LLM接続5件は成功し、利用者による調査画面のブラウザ動作確認も実施済み。画面からのA〜E全件とスマホ幅・キーボード・実IMEの個別確認は未確認。[検証記録](history/frontend-verification.md)で区別する。

1. `main.tsx`を起動処理に留め、`App.tsx`・必要な表示部品・API通信処理を分ける。API応答の型と形式確認を用意する。
2. 質問入力、文字数制限、IME対応の送信ショートカット、5シナリオの質問例を実装する。
3. `/api/agent`への送信、経過時間、960秒の期限、待機終了、重複送信防止、古い応答の反映防止を実装する。HTTP・通信エラーを区別し、入力を保持する。
4. 回答、複数の未解決事項、曖昧性の候補、根拠、成功・失敗のTool履歴、公開JSONを表示する。
5. PCの2列・スマホの1列、折りたたみ、キーボード操作、状態通知を整える。
6. 重要な振る舞いに絞った自動テストを追加する。重複送信防止、APIエラー、待機終了後の古い応答の扱いを優先する。配置・CSS・文言を固定するスナップショットテストは作らず、見た目はブラウザで確認する。
7. 型チェック・ビルド・画面テストをCIへ組み込み、ブラウザから実LLMのA〜Eを確認する。結果は成功件数/実行件数を記録し、偽APIテストと区別する。
8. README・実行ガイド・設計書の実装状態を更新する。コミット・プッシュは利用者の指示に従う。

新しい機能や本番向けの仕組みは追加せず、本書のUI範囲に留める。
