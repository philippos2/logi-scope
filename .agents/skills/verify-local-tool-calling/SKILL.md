# ローカルTool Callingの検証

リポジトリルートの`docs/design.md`の「検証」と「未決定事項」、`docs/requirements.md`のLLM制約を読む。既存検証スクリプトがあれば再利用する。まだなければ最小の検証を作り、本格的なアプリ実装と分ける。

## 検証すること

- アプリが使用するOpenAI互換エンドポイントで日本語質問を送る。Tool呼び出しを解析し、対応するIDで結果を戻し、回答まで進める。
- メモリ上の架空データで、最初の検索結果に含まれるIDを次のToolへ引き継ぐことを確認する。選択順序を検証側でハードコードして成功を演出しない。
- 該当なし、複数候補、引数検証エラーを返し、捏造・任意候補の選択を避けることと、1回の引数修正を確認する。
- 数回繰り返す。名前・JSON構造・呼び出しID・結果投入の互換性を確認し、失敗も報告する。

モデル名、サーバー版、量子化、コンテキスト、推論設定、OS/RAM/GPU、所要時間、ケース別の成否を記録する。利用者が用意していないモデルの巨大ダウンロードを当然の前提にしない。実行環境が不足していれば、その条件と未検証の項目を報告する。

## 記録と終了条件

Tool名・引数・公開可能な結果の要約・失敗分類だけを記録する。Chain-of-Thought、内部推論、生LLM応答全体、認証情報をログや成果物へ保存しない。

検証には有限の呼び出し回数・期限を付ける。不成立なら、観測した互換性やモデルの問題を報告し、無制限に再試行しない。有料クラウドLLMや固定フローへの代替で成功扱いしない。

採用可能と判断した組み合わせと制限を設計書・READMEへ反映する。これは接続検証であり、完成アプリのA〜E受入成功とは区別する。
